# Phase 3B Multi-Instance SWE-EVO Pilot Proposal

Status: proposed experiment parameters; no live authorization. This document
does not publish an approved decision artifact, freeze a scored taskpack, or
permit provider calls.

## Purpose

Run the first scored, complexity-stratified SWE-EVO pilot comparing
`single_codex`, `agentteam_direct`, and `agentteam_full`. The pilot answers a
narrow engineering question: on a small set of long-horizon repository tasks,
does either AgentTeam path preserve solution quality while providing a
measurable orchestration benefit at an acceptable token and wall-time cost?

This is a mechanism and feasibility pilot. Three instances cannot support a
population-level benchmark claim or a statistically powered non-inferiority
claim. Its result decides whether to scale the experiment, revise the runtime,
or stop the current route.

The proposal inherits the provider-free preparation contract in
[`2026-08-10-phase3b-live-pilot-preparation.md`](2026-08-10-phase3b-live-pilot-preparation.md)
and the completed calibration in
[`2026-08-11-phase3b-swe-evo-minimal-calibration.md`](2026-08-11-phase3b-swe-evo-minimal-calibration.md).

## Complexity Proxy

Use `dataset_pr_record_count`, defined as the number of records in the
dataset's `PRs` list for an instance:

```text
dataset_pr_record_count = len(instance["PRs"])
```

This is a preregistered, gold-blind selection proxy, not the official paper's
empirical difficulty label. The paper's difficulty groups depend on observed
model/scaffold outcomes and therefore cannot be used for prospective
selection. The proxy is justified only as visible repository-evolution
metadata: the SWE-EVO analysis reports an association between linked pull
request count and empirical task difficulty.

The extraction must run in a trusted evaluator-side projection step over the
exact Arrow artifact. Only the resulting `complexity_stratum`, `instance_id`,
and repository identifier may enter the routing manifest. Raw PR records,
patches, tests, scores, and prior outcomes must remain outside all
runtime-visible roots. The stratum and its source count are control-plane
metadata and must not be included in the worker prompt.

The observed distribution produces these fixed boundaries:

| Stratum | Boundary | Population before exclusion | Eligible population |
| --- | --- | ---: | ---: |
| `low` | 0-2 PR records | 21 | 20 |
| `medium` | 3-6 PR records | 12 | 12 |
| `high` | 7 or more PR records | 15 | 15 |

The implementation must independently reproduce all 48 counts, the boundary
populations, and the 47-instance eligible population before selection can be
frozen. A mismatch is terminal preparation evidence, not permission to adjust
the boundaries.

## Execution Profile

- Modes: `single_codex`, `agentteam_direct`, `agentteam_full`.
- Model: `gpt-5.6-sol`.
- Reasoning profile: `high`.
- Initial repetitions: two per instance and mode.
- Maximum repetitions: three per instance and mode.
- Provider concurrency: one model invocation at a time.
- Session policy: fresh model session and isolated work root per execution.
- Mode order: use the preregistration's three counterbalanced permutations,
  assigning one permutation to each selected instance deterministically.
- Retries: provider transport and rate-limit failures only; no semantic repair
  retry outside the frozen mode behavior.
- Operator interaction during an execution: none. A request for corrective
  input becomes terminal evidence for that execution.

The model and reasoning profile preserve comparability with the completed
calibration. A lower-cost model-routing experiment is a separate ablation and
must not be introduced into this pilot after selection.

For `agentteam_direct`, one deterministic taskpack per selected instance must
be reviewed and frozen before any scored outcome is visible, then reused
unchanged across repetitions. Its preparation cost is reported separately and
is not scored as execution cost. For `agentteam_full`, live taskpack authoring
is part of the mode and its provider usage is included in that execution's
budget and cost.

## Local Resource Policy

Resource limits protect the host and make failures attributable; they are not
intended to force a multi-agent runtime into the footprint of one Codex
process. The pilot therefore separates a common workload slot from AgentTeam's
additional control-plane allowance.

This refines the inherited equal-resource rule: equal `cpu_limit` and
`memory_limit_bytes` continue to describe the common workload slot, while an
additive, mode-specific parent envelope accounts for orchestration. It does
not retroactively change any frozen Phase 3A or calibration artifact.

| Scope | CPU quota | Memory high | Memory max | Tasks max |
| --- | ---: | ---: | ---: | ---: |
| Common workload slot | 4 CPUs | 8 GiB | 12 GiB | 256 |
| `single_codex` total envelope | 4 CPUs | 8 GiB | 12 GiB | 256 |
| AgentTeam control-plane allowance | 4 CPUs | 8 GiB | 12 GiB | 256 |
| Each AgentTeam mode total envelope | 8 CPUs | 16 GiB | 24 GiB | 512 |
| Whole pilot project hard envelope | 16 CPUs | 32 GiB | 48 GiB | 1,024 |

The common workload slot covers the active coding worker and repository test
processes. The same slot limit applies in all three modes. The AgentTeam
allowance covers the scheduler, author, repo mapper, reviewer, reporting, and
other control-plane processes. It may not silently increase one worker's
workload slot. If a later protocol permits several concurrent workers, the
contract must explicitly allocate one workload slot per active worker and
raise the project envelope before authorization.

The official evaluator always uses the common workload-slot limit, regardless
of which mode produced the candidate. Model invocation concurrency remains one
for this pilot, and mode executions remain sequential. Set `MemoryHigh` as the
soft pressure boundary, `MemoryMax` as the hard boundary, and
`MemorySwapMax=0` so a run cannot appear to survive by causing uncontrolled
host paging. CPU quotas are ceilings, not reservations.

This intentionally gives AgentTeam a larger total local-resource envelope. It
is part of the system-under-test cost and must be disclosed rather than hidden
as equal resources. Record per execution:

- CPU time and peak resident memory for the workload slot;
- CPU time and peak resident memory for the AgentTeam control plane;
- cgroup OOM, PID-limit, CPU-throttling, and timeout counters;
- the existing provider-token and wall-time metrics.

Quality remains paired under an equal workload slot. Wall-time comparisons
remain valid as observed system latency but must be interpreted together with
the additional AgentTeam CPU and memory consumption. A future efficiency claim
should report both wall time and aggregate CPU time.

## Budget

Each instance/mode/repetition receives the same hard ceiling:

- maximum total provider tokens: `1,500,000`;
- maximum provider wall time: `1,800` seconds.

The initial schedule contains 18 executions:

```text
3 instances * 3 modes * 2 repetitions = 18 executions
```

Its aggregate authorization ceiling is therefore 27,000,000 tokens and
32,400 provider wall seconds. If every pair triggers a third repetition, the
absolute maximum is 27 executions, 40,500,000 tokens, and 48,600 provider wall
seconds. A third repetition is admitted only when the first two terminal
outcomes disagree or their token or wall-time values trigger the existing
greater-than-30-percent variance rule.

The one-instance calibration consumed 1,622,220 tokens across all modes and is
useful for feasibility only. It is not used to lower the hard ceiling because
the selected tasks may require substantially longer repository work. Unused
budget is not transferable between executions.

## Metrics And Decision Rule

The existing preregistration remains authoritative:

- primary metric: `final_mechanical_acceptance`, determined only by the
  benchmark evaluator;
- benchmark-native partial score and the frozen SWE-style partial score are
  reported as secondary diagnostic resolution measures;
- token accounting requires 100 percent provider-usage coverage;
- uncached work is `max(input-cached_input,0)+output`;
- reasoning tokens are reported only when the provider declares them
  non-overlapping and are never added twice.

Proposed thresholds:

- non-inferiority margin: `0.10` absolute primary acceptance rate;
- maximum median paired total-token ratio versus `single_codex`: `2.0`;
- maximum median paired provider-wall ratio versus `single_codex`: `2.0`;
- preselected secondary benefit metric: `regressions`.

Evaluate `agentteam_direct` and `agentteam_full` independently against the
paired `single_codex` executions. A mode continues to a larger study only when
all cost caps pass and either:

1. its primary acceptance rate is higher; or
2. its primary acceptance rate is within the non-inferiority margin and its
   regression count is lower.

Equal primary quality with equal regressions is not evidence of benefit and
does not justify scaling under this rule. A three-instance result is an
engineering continuation gate, not a statistical confidence statement.
Report per-instance pairs and raw repetition outcomes in addition to aggregate
rates and medians so that one task cannot be hidden by an average.

## Preparation Work Before Authorization

### P3B-01A: Trusted complexity projection

Add a deterministic Arrow-to-routing projection that:

- verifies source commit, artifact hash, split, and row count;
- derives only `dataset_pr_record_count` and the fixed stratum;
- emits only allowlisted routing fields;
- proves forbidden evaluator fields cannot cross the boundary;
- records source and output digests plus population counts;
- reproduces the expected selection preview in a test fixture bound to the
  exact official artifact metadata.

The current inventory converter accepts an existing `complexity_stratum`; it
does not derive one from the Arrow source. The pilot cannot freeze until this
gap is implemented and reviewed.

### P3B-01B: Resource-envelope enforcement

Bind the resource table above into the per-mode execution contract and enforce
it over the complete descendant process tree:

- apply the common workload slot to single Codex, every AgentTeam worker, and
  every official evaluator invocation;
- apply the larger mode envelope to all AgentTeam control-plane and workload
  descendants together;
- apply the project envelope across the complete pilot run;
- reject launch when the host cannot provide the frozen envelope with reserved
  scheduler and operating-system headroom;
- persist cgroup identity and resource counters in terminal evidence;
- classify OOM, PID exhaustion, and resource-driven timeout as
  `resource_limit_exhausted`, not model-quality failure;
- prove cleanup removes or drains every descendant before the next mode starts.

Represent the common workload slot with the existing preregistration fields.
Add an explicitly versioned resource-envelope binding for the project and mode
parents rather than overloading those shared fields. On Linux, place transient
services beneath a run-specific project slice and mode slice; enforce the
project and mode ceilings on their parent slices and the workload ceiling on
the leaf service. The binding must fail closed on systems that cannot enforce
or read back the hierarchy.

The current schemas contain `cpu_limit` and `memory_limit_bytes`, and the
bounded evaluator path applies `CPUQuota`, `MemoryMax`, and `TasksMax`. The
model-worker transient service does not yet apply equivalent limits. Merely
recording resource fields is insufficient; live authorization remains blocked
until enforcement and negative tests cover the model-worker path.

### P3B-01C: Approved decision and selection artifacts

After operator approval of this proposal, publish one immutable
`phase3_pilot_decisions.v1` artifact containing these parameters, then
materialize and replay the canonical selection. Approval must be explicit;
this Markdown proposal is not a substitute for the decision artifact.

### P3B-02: Per-instance freeze

For each selected instance:

- verify the exact target commit and official evaluator image;
- construct the common visible goal and acceptance interface;
- review and freeze the direct-mode taskpack;
- build one immutable per-instance preregistration binding equal inputs,
  budgets, model profile, isolation, mode order, and taskpack digest;
- prove that no gold or sibling-mode artifact is visible.

### P3B-03: Aggregate provider-free preflight

Build the aggregate pilot contract and verify:

- all three instance bindings and aggregate ceilings;
- container/runtime availability for every selected instance;
- provider credentials and model availability without consuming a scored
  call;
- fresh work-root creation, candidate retention, official evaluation, and
  complete usage accounting paths;
- zero scored provider calls during preparation.

### P3B-04: Mandatory operator gate

Present the decision artifact, selected IDs, direct taskpacks, preflight
receipt, exact runtime release, aggregate maximum cost, and abort conditions.
Pause for one epoch-bound `P3-LIVE` authorization. Any subsequent change to a
selected instance, taskpack, model, budget, runtime release, evaluator, or
authority digest invalidates that authorization.

### P3B-05: Scored execution and reporting

Execute the admitted schedule, evaluate sealed candidate patches with the
official evaluator, trigger third repetitions mechanically, and publish one
report containing:

- every terminal outcome and official score;
- paired quality, regression, token, uncached-work, and wall-time results;
- full-mode authoring and worker stage costs;
- direct taskpack preparation cost reported outside scored execution cost;
- all infrastructure failures, retries, usage gaps, and stop conditions;
- the continuation decision for each AgentTeam mode.

No candidate patch may be merged into its benchmark repository. The pilot
evaluates candidates; it does not operate a production integration workflow.

## Stop Conditions

Stop before live authorization if any of these conditions holds:

- the trusted projection cannot be reproduced from the exact Arrow artifact;
- selection depends on gold, prior outcomes, or model judgment;
- the canonical selection differs from the preview without an explained code
  or source discrepancy;
- a selected target commit or official evaluator image is unavailable;
- direct taskpacks are not frozen before scored outcomes;
- full-mode authoring and worker usage cannot share one enforced budget;
- any required workload, mode, or project resource envelope is recorded but
  not enforced over its full descendant process tree;
- any mode receives different visible task inputs, tools, permissions, or
  evaluator conditions;
- aggregate authorization would exceed the ceilings in this proposal;
- the runtime release or an authority digest changes after approval.

During execution, stop the affected run on gold leakage, sibling-mode artifact
visibility, incomplete provider usage, budget exhaustion, authority drift, or
an unclassified semantic retry. Retain the terminal evidence; do not silently
replace the instance or rerun under a revised protocol.

## Approval Boundary

Operator acceptance of this proposal authorizes only `P3B-01A` through
provider-free `P3B-03` preparation and publication of the corresponding
approved decision artifact. It does not authorize `P3B-05`. Real scored calls
require the separate `P3B-04` review and epoch-bound live authorization after
all selected inputs and aggregate costs are visible.
