# Phase 3 自适应实现与控制器验证实验

## 结论

这条路径值得继续测试，但暂不设为默认流程。

在固定 DVC 实例上，流程只启动了一个实现 worker，没有单独启动定位
worker，也没有启动修复 worker。正式评分与旧固定三阶段候选完全相同：
F2P 为 `2/14`，P2P 为 `64/66`，partial score 为 `0.393939`，实例仍未完全
解决。

与有效的固定三阶段 v2 相比：

- 总 token 从 `766760` 降至 `645964`，减少 `15.754%`；
- 未缓存输入从 `167551` 降至 `127300`，减少 `24.023%`；
- 模型执行时间从 `717s` 降至 `548s`，减少 `23.57%`；
- 模型命令数从 `52` 降至 `37`，减少 `28.846%`；
- checkpoint 从 `8357` bytes 降至 `3021` bytes，减少 `63.851%`。

因此，在这一个实例上，删除单独的模型定位调用确实降低了成本，而且没有
降低正式评分。

## 验证结果

worker 因工具调用预算耗尽，按合同返回了验证移交，而不是宣称任务已经
通过。控制器随后完成了以下检查：

- 修改后的 Python 文件可编译；
- 在完整公开 DVC 环境中，16 个命令和列表单元测试通过；
- worker 新增的 2 个 `no-download` 功能测试失败。

这两个功能测试调用 `dvc.pull()` 时没有配置默认 DVC remote，因而抛出
`NoRemoteError`。这证明候选还不能合并，也说明控制器验证不能只停留在宿主
默认 Python 环境。最初宿主环境缺少 `dvc_ssh`，控制器正确地没有要求修复
worker 改代码；人工切换到冻结的公开测试环境后，才发现测试本身的问题。

## 执行记录

模型日志中有 `37` 个完成的命令，覆盖了任务声明的全部 17 个源码和测试
路径，命令文本均不相同。由于只有一次模型调用，跨调用重复读取为 `0`。
第一轮执行记录只做统计，没有向模型注入状态、阻止命令或复用旧结果。由于
没有发现完全相同的重复命令，本轮没有证据支持立即开发命令结果复用功能。

## 限制

- 只测了一个 SWE-EVO 实例，不能推断整体 benchmark 表现；
- 正式评分与旧候选相同，但仍未完全解决任务；
- 单次模型调用最终使用 `645964` tokens，超过 `600000` 的轮间预算线，说明
  当前预算只能阻止下一次调用，不能中断正在运行的调用；
- 控制器验证环境还未在启动前绑定到公开测试环境。

## 后续

保留“实现优先、控制器验证、失败时条件修复”的方向，先补齐验证环境绑定，
再用第二个固定实例复测。命令结果复用继续关闭，等观察数据证明存在可复用的
重复工作后再单独实验。
